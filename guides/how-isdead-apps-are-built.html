How each IsDead app is built

Updated October 26, 2026 · about 5 min read

Every app on YourAppIsDead follows the same set of rules, whether it replaces a scheduling tool or a screenshot utility. This page explains those rules, the shared technology underneath, where the apps differ, and how you can contribute a fix or request a new app.

The shape of every app

Each app is named after the product it replaces, as <Product>IsDead, and lives at yourappisdead.com/<product>isdead. The contributing guide asks for three surfaces:

  1. A marketing page that follows the structure and tone of the original product's homepage, written in our own words. Most include a price comparison.
  2. A login page at /<product>isdead/login.
  3. The app itself, usually at /<product>isdead/app.

Many of the web apps also let you start without an account: you get a guest session, and your work moves to your account if you sign in later. Desktop apps replace the third surface with a download link to a signed Mac build.

The rules

One repository per app

Every app has its own public repository, so people can contribute to the one they care about without wading through the others. The marketplace repository holds only the homepage, the apps.json listing, the games and shared documentation.

Original assets only

No app may copy logos, icons, illustrations, screenshots, marketing copy or source code from the product it replaces. The look is recreated with original art, and the product's name is used only to say what the app replaces. Some READMEs go further; CalendlyIsDead's notes, for instance, rule out copying code from another open-source scheduler whose copyleft license would conflict with the project's own.

Shared sign-in

Apps do not roll their own account systems. They all use one shared Firebase Authentication project with email and password or Google sign-in. After you sign in, the server verifies the Firebase token and sets a session cookie scoped to the whole site, so one sign-in covers every app. Keys and service accounts are never committed; contributors ask a maintainer for configuration. Without that configuration, a local copy shows "Sign-in not configured" and offers a demo account instead.

Shared design system, unique font

Colors, spacing and components come from a shared design system, vendored into each repository, with a theme per app. Each app picks its own lookalike typeface under an open font license (OFL, Apache or MIT), standing in for the original's proprietary font. Examples from the READMEs: Lexend for BitlyIsDead, Bricolage Grotesque for LinktreeIsDead, Urbanist for LoomIsDead, Familjen Grotesk for WeTransferIsDead and Inter Tight for LinearIsDead.

Free, with nothing paywalled

The apps and their hosted versions are free with no locked features. Where the original has an upgrade screen, the clone's version never takes payment.

Good citizenship: mobile and accessibility

Each app should work on screens from 360 pixels wide, be usable from the keyboard, and respect the prefers-reduced-motion setting for people who are sensitive to animation. Several repos include automated checks at phone widths, such as a 390-pixel horizontal-scroll test.

Licensing

Each repository carries its own LICENSE file, and that file is what applies. Today the marketplace and nearly every app use Apache-2.0, a permissive license with an explicit patent grant. SuperhumanIsDead is the exception and uses MIT. Both let you use, modify and redistribute the code, including commercially, as long as you keep the notices. Fonts bundled with the apps are under the SIL Open Font License.

The common stack

Most of the web apps share a stack, which makes it easier to move between them:

  • Next.js with the App Router and TypeScript, served under a base path such as /trelloisdead.
  • Vercel for hosting. The marketplace's vercel.json has two rewrites per app that send /<slug> to that app's own Vercel project, so every app shares the yourappisdead.com origin. A CI check rejects rewrites to any other host.
  • Vitest for unit tests and Playwright for browser smoke tests, usually run with npm test and npm run shots.
  • Pure core logic: many apps keep their data model in plain functions (for example lib/linear/model.ts or lib/otter/model.ts) so it can be unit tested without a browser.

The desktop apps

Four Mac apps are native Swift projects: GranolaIsDead, WisprFlowIsDead, CleanShotXIsDead and LoomIsDead's recorder. They require macOS 14.2 or later, are signed and notarized for distribution, and update automatically through Sparkle. Speech features in GranolaIsDead and WisprFlowIsDead run on the device. SuperhumanIsDead is an Electron app that talks directly to Gmail with your own OAuth client and has no server of its own.

Honest about gaps

Each README has a "known gaps" or "not built" section, and several repos keep a parity report in docs/PARITY_REPORT.md that records what was checked against the original and what remains. These are young projects, and some READMEs describe themselves as work in progress. Reading those sections before you rely on an app is the single most useful thing you can do. Our guide to judging open-source software explains what else to look for.

How to contribute

  • Improve an existing app. Every listing links to its repository. Issues and pull requests are open. Keep pull requests small and focused, fill in the template, and follow the code of conduct.
  • Build a new clone. Follow the rules above in a new repository, then open a pull request that adds an entry to apps.json with a name, slug, category, one-sentence blurb, status (live, soon or community) and the public repo URL. A maintainer adds the routing once your app is deployed.
  • Improve the site. The homepage is static HTML with no build step, and pull requests are welcome.
  • Never commit secrets or third-party assets without an open license.

How to request an app

If there is a subscription you would like to see replaced, use the "Submit an app to kill" form on the homepage, or open an issue in the marketplace repository with the matching template. Requests that describe the specific job you need done, rather than only the product name, are the easiest to act on.
