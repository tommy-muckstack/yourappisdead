How to self-host an open-source SaaS app

Updated October 26, 2026 · about 6 min read

Self-hosting means running your own copy of an app: your server or hosting account, your database, your domain. It gives you control over your data and removes per-seat fees, but it makes you the operator. This guide covers the practical steps in a vendor-neutral way, using the IsDead apps as worked examples because their READMEs spell out exactly what they need.

1. Read the README before anything else

A good README tells you three things: how to run the app locally, which environment variables it needs in production, and what is not built yet. Read all three. The "known gaps" section matters most, because it tells you whether the app can do your job today. Several IsDead READMEs, for example, say plainly that data is stored in the browser and that a server-side store is still to come.

Also check the license file. Permissive licenses such as Apache-2.0 and MIT let you run and modify the code with few conditions; our guide to judging open-source apps explains the differences.

2. Fork, clone and run it locally

Fork the repository so you have your own copy to deploy from, then clone it and run it on your machine first. Most IsDead web apps are Next.js projects and start the same way:

  • npm install (or npm ci for an exact install from the lockfile)
  • npm run dev, then open the local URL, which includes the app's base path, such as /trelloisdead
  • npm test and npm run typecheck to confirm your copy is healthy

Many apps include a demo account that works locally without any keys, and some fall back to an embedded or file-based store. CalendlyIsDead, for instance, runs an embedded Postgres in development and prints booking emails to the server log. Use that to explore before you create any accounts.

3. Set environment variables, and keep them secret

Configuration lives in environment variables, not in code. Typical ones are a database connection string, a secret for signing session cookies, API keys for email and payments, and the public URL of the app. The IsDead web apps commonly use:

  • NEXT_PUBLIC_FIREBASE_* and FIREBASE_SERVICE_ACCOUNT_JSON for sign-in and, in some apps, storage
  • AUTH_SECRET for signing guest and session cookies
  • DATABASE_URL for apps that use Postgres, such as CalendlyIsDead
  • APP_URL so the app can build absolute links in emails and OAuth callbacks

Rules that apply everywhere: never commit secrets to Git, generate long random values for signing secrets, use separate keys for development and production, and set them in your host's environment settings. Variables prefixed with NEXT_PUBLIC_ are exposed to the browser, so only put non-secret values there.

4. Choose where the data lives

This is the decision that most affects reliability. Serverless hosts usually give your app a temporary disk that disappears between requests or deploys, so anything written to local files can vanish. The IsDead READMEs are explicit about this: TypeformIsDead warns that its JSON-file store works locally but not on Vercel, and WeTransferIsDead notes that production needs object storage for file bytes.

5. Set up authentication

Every IsDead web app signs people in through Firebase Authentication with email and password or Google. If you self-host, create your own Firebase project, enable those providers, add your domain to the project's authorized domains, and fill in the Firebase variables. Without them the apps show "Sign-in not configured" on the login page. If you add third-party sign-in or calendar connections, register the exact callback URLs, including the base path, with each provider; a mismatch is the most common cause of OAuth errors.

6. Set up email sending

Apps that send email need a transactional email provider and a verified sending domain. CalendlyIsDead and DocuSignIsDead both use Resend when an API key is set, and simply log messages otherwise. Whatever provider you use, add the SPF and DKIM DNS records it gives you, send from a domain you control, and test that messages reach a real inbox rather than spam.

7. Know your host's limits

Read the limits of your hosting platform before you trust it with files or long jobs. Vercel caps function request bodies at 4.5 MB, which is why LoomIsDead uploads recordings straight to blob storage and the hosted WeTransferIsDead rejects large uploads. Scheduled work needs a scheduler: CalendlyIsDead sends reminder workflows from a cron job every five minutes, protected by a CRON_SECRET.

8. Add a custom domain

Point a domain or subdomain at your deployment using the DNS records your host provides, and wait for HTTPS certificates to be issued. If the app runs under a sub-path, as every IsDead app does (Next.js basePath), keep the path consistent in APP_URL, OAuth callbacks and webhooks. Some features depend on owning the whole host: BitlyIsDead verifies custom short domains by DNS, but routing them needs a self-hosted copy.

9. Back up, and test the restore

A backup you have never restored is a hope, not a backup. Schedule exports from your database (for Postgres, pg_dump or your provider's point-in-time recovery; for Firestore, its managed export) and keep a copy somewhere separate from the host. For browser-only apps, use the built-in exports: Markdown from NotionIsDead, JSON and CSV from LinearIsDead, a backup file from CanvaIsDead, and an encrypted backup from 1PasswordIsDead. Try restoring into a fresh copy at least once.

10. Plan for updates

Add the original repository as an upstream remote, then periodically fetch and merge its changes into your fork. Run the tests and type checks before you deploy, deploy to a preview environment first if your host supports it, and read the commit history for anything that touches the database schema or environment variables. Keep your own changes small and well separated so merges stay easy.

11. Count the real cost

Self-hosting removes subscription fees but adds infrastructure: hosting, a database, email sending, file storage, a domain, and your time. Many providers have free tiers that cover a small team, but limits and prices change, so check each provider's current pricing page rather than relying on a figure you read somewhere. The largest cost is usually attention: someone has to notice when something breaks.

What about the desktop apps?

The Mac apps (GranolaIsDead, WisprFlowIsDead, CleanShotXIsDead, LoomIsDead's recorder and SuperhumanIsDead) have no server for you to host. You download them or build them from source with the scripts in each repo. SuperhumanIsDead asks you for your own Google OAuth client, since Google does not let apps share one. Distributing your own build to other people requires an Apple Developer ID for signing and notarization.

Self-hosting checklist

  • Read the README's gaps section and the LICENSE file
  • Fork, run locally, and pass npm test
  • Create production secrets; store them only in the host's settings
  • Choose a durable database; avoid local files on serverless hosts
  • Set up your own auth project and register exact callback URLs
  • Verify an email sending domain with SPF and DKIM
  • Check request size, timeout and cron limits
  • Connect a custom domain with HTTPS
  • Schedule backups and do a test restore
  • Add an upstream remote and a routine for updates
  • Write down what it costs each month, including your time
