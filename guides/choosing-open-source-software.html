How to judge an open-source app before you rely on it

Updated October 26, 2026 · about 5 min read

"Open source" tells you the code is public and the license lets you use it. It does not tell you whether the project is maintained, secure, or a safe home for your data. Before you move real work into any open-source app, including the ones on this site, spend twenty minutes checking six things: the license, project activity, security, data export, hosting, and support.

1. The license: what you are allowed to do

A license is the legal permission to use, change and share the code. Without one, public code is not actually open source. Most licenses fall into two families.

Permissive licenses

Permissive licenses, such as MIT, Apache-2.0 and the BSD licenses, let you use, modify and redistribute the code, including in commercial and closed-source products, as long as you keep the copyright and license notices. Apache-2.0 adds an explicit patent grant from contributors and asks you to note significant changes, which some organizations prefer. For someone who just wants to run a tool, permissive licenses impose almost no obligations.

Copyleft licenses

Copyleft licenses, such as the GPL family, also let you use and modify the code, but if you distribute a modified version you must release your changes under the same license. The AGPL extends this to software offered over a network: if you modify an AGPL web app and let other people use it, you must offer them your modified source. Copyleft is not a problem for ordinary users running the software unchanged. It matters if you plan to modify the code and offer it to others, or to combine it with code under a different license.

Watch for "source-available"

Some projects publish code under licenses that restrict commercial use or competing services. Those can be perfectly reasonable, but they are not open source in the usual sense, and the restrictions may affect you. Always read the actual LICENSE file rather than a badge or a marketing page.

2. Project activity: is anyone home?

Open the repository and look at:

  • Recent commits and releases. Steady activity over months is a good sign. A burst of work followed by silence is a warning.
  • Issues. Are bugs acknowledged and closed? How long do they sit without a reply?
  • Contributors. A project maintained by one person can be excellent, but it depends on that person. Several active contributors reduce the risk of it stalling.
  • Age. Older projects have had more time for bugs to be found. Newer projects may move faster but have rougher edges.
  • Tests and documentation. A test suite and a README that explains setup and limitations show care.

3. Security: has anyone checked?

Public code can be inspected, but that does not mean anyone has. Look for:

  • A security policy (often SECURITY.md) explaining how to report problems privately.
  • Independent audits, especially for anything holding passwords, financial data or personal information. Ask whether the audit report is published and how recent it is.
  • Clear threat models: honest projects say what they do not protect against.
  • Dependency hygiene: a lockfile, and evidence that dependencies are updated.
  • Secret handling: no keys committed to the repository, and configuration kept in environment variables.

4. Data export: can you leave?

The best protection against any software, paid or free, is being able to take your data with you. Check that you can export everything in an open format (CSV, JSON, Markdown, standard PDF or the original files), that the export is complete rather than partial, and that you can import it back. Then actually try it once. Also find out where data lives: on a server, in a cloud database, or only in your browser, where clearing site data can delete it.

5. Self-hosted or hosted?

Many open-source apps can be used two ways. A hosted version run by the project is convenient, but you rely on the project to keep it running and to treat your data well. A self-hosted copy gives you control, but you take on updates, backups and uptime yourself. Our self-hosting guide covers what that involves. The open license is what makes both options possible: if a hosted service disappears, the code does not.

6. Support: who helps when it breaks?

Paid products usually come with a support team and a service-level agreement. Open-source projects usually offer an issue tracker and documentation, sometimes a community forum, and occasionally paid support from the maintainers or a company. Decide in advance what happens if the tool fails on a deadline. For a personal side project, waiting for a fix may be fine. For anything customers depend on, it may not be.

Applying this honestly to the IsDead apps

It would be odd to publish this checklist and not run our own apps through it. Here is a fair assessment.

  • License: strong. Each repository has a LICENSE file. Nearly all use Apache-2.0; SuperhumanIsDead uses MIT. Both are permissive. Bundled fonts are under the Open Font License.
  • Activity and maturity: young. These are new projects. Several READMEs describe their app as a work in progress, and none has years of production use behind it. Expect rough edges, and check each repository's history yourself.
  • Security: varies, and mostly unaudited. 1PasswordIsDead states plainly that it is experimental and has not been independently audited, and its security notes list what it does not protect against. We would not recommend it as the only place for important passwords. No other IsDead app claims an independent audit either.
  • Data export: mostly good, with a caveat. Many apps export to open formats (Markdown from NotionIsDead, CSV from AirtableIsDead and TypeformIsDead, JSON and CSV from LinearIsDead, SVG and JSON from MiroIsDead). But several store data only in your browser, with no sync, so regular exports are essential.
  • Hosting: both options. Many apps run on yourappisdead.com and every web app can be self-hosted from its repository, though some need extra setup, such as object storage, before they work well outside a local machine.
  • Support: community only. There is no support desk or uptime guarantee. Help comes through each repository's issues.

In short: the IsDead apps are a good fit for low-risk, single-purpose jobs, for learning, and for trying a free alternative before you cancel a subscription. For anything critical, use them alongside a backup, or choose a more established tool until they mature. The guide to how the apps are built explains their setup in more detail.

A 20-minute checklist

  • Read the LICENSE file and note whether it is permissive or copyleft
  • Check the date of the last commit and last release
  • Skim open issues and how quickly maintainers reply
  • Read the README's known gaps
  • Look for a security policy and any audit reports
  • Export some test data and import it back
  • Decide whether you will use the hosted version or self-host
  • Write down your plan if the project stops being maintained
